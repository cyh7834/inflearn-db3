# 12. 물리적 모델링 - 실습

## 1. 물리적 모델링 순서 및 핵심 목표

-   **순서**: 테이블/컬럼 변환, 데이터 타입 정의, 제약 조건 설정, 인덱스 설계, 역정규화 및 성능 튜닝, 파티셔닝/샤딩 등 고급 기법 적용, 뷰/저장 프로시저/함수/트리거 생성.
-   **핵심 목표**: 성능 최적화. 데이터 검색 속도를 획기적으로 높이는 인덱스 설계와 역정규화 기법 적용에 중점.

## 2. 인덱스 설계 실습

-   **인덱스의 필요성**: 데이터베이스 테이블의 특정 컬럼(들) 데이터를 빠르게 찾기 위함. 인덱스 없이는 풀 테이블 스캔(Full Table Scan)으로 인한 성능 저하 발생.
-   **MySQL 인덱스 자동 생성**: Primary Key(PK), Unique Key(UK), Foreign Key(FK) 설정 시 자동으로 해당 컬럼에 인덱스 생성.

-   **주요 시나리오별 인덱스 설계**:
    -   **로그인 및 중복 ID, 이메일 체크**: `login_id` 및 `email` 컬럼에 `UNIQUE` 제약조건을 통한 인덱스 자동 생성으로 최적화. `member_id`와 같은 PK 인덱스도 효율적임.
    -   **회원 주문 목록 조회**: `orders` 테이블의 `member_id` 컬럼에 인덱스를 추가하여 특정 회원의 주문을 빠르게 조회.
    -   **상품명으로 상품 검색**: `product` 테이블의 `product_name` 컬럼에 인덱스를 추가. `LIKE '%검색어%'`와 같이 검색어 앞에 `%`가 붙는 경우 B-Tree 인덱스 성능에 한계가 있어 전문 검색 엔진 고려. `LIKE '검색어%'`의 경우 인덱스 효과적.
    -   **관리자의 주문 상태 및 기간별 조회 (복합 인덱스)**: `orders` 테이블에 `(order_status, ordered_at)` 복합 인덱스 추가. 복합 인덱스 컬럼 순서는 선택도 높은 컬럼(`order_status`)을 앞에 두는 것이 일반적.
    -   **사용자의 주문 상태 및 기간별 조회 (member_id 조건 포함)**: `member_id`의 선택도가 압도적으로 높으므로, `member_id` 인덱스를 우선 사용. 추가적인 복합 인덱스는 과잉 최적화가 될 수 있음.
-   **인덱스 비용**: 인덱스는 저장 공간을 차지하고 쓰기(INSERT, UPDATE, DELETE) 성능을 저하시키므로 신중하게 추가.
-   **실무 기준**: 데이터 분포와 조회 효율성, 쓰기 작업의 빈도와 중요도, 실제 쿼리 패턴과 성능 측정을 기반으로 판단. 예상만으로 섣불리 추가하기보다 실제 병목 지점을 데이터로 확인 후 적용 권장.

## 3. 역정규화 실습

-   **목표**: 조회 성능 향상.
-   **중복 컬럼 추가**: `order_item` 테이블에 `product_name` 컬럼을 추가하여 주문 내역 조회 시 `product` 테이블과의 `JOIN` 불필요. (스냅샷 데이터로서 비즈니스 요구사항 만족)
-   **파생 컬럼 추가 (계산된 값 저장)**: `orders` 테이블에 `total_amount` 컬럼을 추가하여 총 주문 금액 계산을 위한 복잡한 집계 쿼리 불필요.
-   **테이블 통합 검토**: `orders`와 `delivery` 테이블 통합 제안에 대한 신중한 검토. 데이터의 생명주기, 변경 빈도, 책임과 응집도, 확장성, 성능 이점 등을 고려했을 때 분리된 상태를 유지하는 것이 바람직하다는 결론.

## 4. 쇼핑몰 테이블 정의서 및 DDL 생성

-   **테이블 정의서**: 설계된 테이블 구조를 명세화한 문서. `member`, `product`, `orders`, `order_item`, `delivery`, `pay` 각 테이블에 대한 상세 정의 포함. `created_at`과 `updated_at` 같은 감사 컬럼 추가 및 시스템/비즈니스 시간 구분 강조.
-   **쇼핑몰 DDL 및 DB 만들기**: 완성된 DDL과 샘플 DML(데이터 조작어)을 포함하는 통합 스크립트 작성. 데이터베이스 초기화, 테이블 초기화, 테이블 생성, 샘플 데이터 입력 순서로 구성.
-   **물리적 모델 ERD 자동 생성**: MySQL Workbench와 같은 도구를 사용하여 생성된 테이블 구조를 기반으로 물리적 ERD를 자동으로 생성하여 시각적으로 확인.
