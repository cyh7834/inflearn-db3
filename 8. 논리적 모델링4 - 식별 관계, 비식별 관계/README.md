# 8. 논리적 모델링4 - 식별 관계, 비식별 관계

## 1. 핵심 개념

- **관계의 구분 기준**: 부모 테이블의 기본 키(PK)를 자식 테이블이 자신의 '기본 키(PK)의 일부'로 사용하는지, 아니면 단순히 '일반 컬럼(FK)'으로만 사용하는지에 따라 구분됨.

- **식별 관계 (Identifying Relationship)**
  - **정의**: 부모 테이블의 PK를 물려받아 자식 테이블의 PK의 일부로 포함하는 관계임. (복합 키 구성)
  - **특징**: 부모 없이는 자식이 존재할 수 없는 '강한 결합(Tight Coupling)'을 나타냄. 자식의 존재가 부모에게 강력하게 의존적임.
  - **예시**: '아파트 동'과 '호수'의 관계. '101동 502호'에서 '502호'는 '101동'이라는 정보 없이는 고유하게 식별될 수 없음.

- **비식별 관계 (Non-identifying Relationship)**
  - **정의**: 부모 테이블의 PK를 물려받아 자식 테이블의 일반 컬럼(FK)으로만 사용하는 관계임. 자식 테이블은 자신만의 고유한 PK를 가짐.
  - **특징**: '느슨한 결합(Loose Coupling)'을 나타냄. 자식은 부모와 독립적으로 존재할 수 있음.
  - **예시**: '회사'와 '사원'의 관계. '사원'은 '사원번호'라는 고유한 식별자를 가지며, '회사' 정보는 소속을 나타내는 부가 정보가 됨.

## 2. 관계별 장단점 및 설계 방식

### 일대다(1:N) 관계 (예: 게시글-댓글)

- **비식별 관계 (권장)**
  - **장점**: 구조가 단순하고 명확하며, 관계 변경(예: 댓글을 다른 게시글로 이동)에 매우 유연함. ORM 기술(JPA/Hibernate 등)과 친화적임.
  - **단점**: PK만 봐서는 부모와의 관계를 직관적으로 알기 어려움.

- **식별 관계**
  - **장점**: PK 자체에 비즈니스 의미('1번 게시글의 3번째 댓글')가 담김.
  - **단점**: 복합키 관리의 복잡성, 유연성 부족, 확장성 저하(대댓글 기능 추가 시 PK가 계속 길어짐) 등의 심각한 문제가 있음.

### 다대다(M:N) 관계 (예: 주문-상품)

- **비식별 관계 (권장)**
  - **설계**: 연결 테이블에 독립적인 PK(대리 키)를 사용하고, 두 부모 테이블의 PK를 각각 FK로 가짐.
  - **특징**: 비즈니스 규칙(예: '하나의 주문에 동일 상품 중복 불가')을 PK가 아닌 `UNIQUE` 제약조건으로 강제함.
  - **장점**: **유연성과 데이터 정합성을 모두 확보**할 수 있음. 비즈니스 규칙이 변경되어도 `UNIQUE` 제약조건만 수정하면 되므로 PK를 변경하는 위험한 작업이 필요 없음. 확장성이 매우 높음.

- **식별 관계**
  - **설계**: 연결 테이블이 양쪽 부모 테이블의 PK를 조합하여 복합 PK를 구성함.
  - **특징**: PK 자체가 비즈니스 규칙을 강제함.
  - **단점**: 규칙 변경 시 PK 자체를 수정해야 하므로 매우 경직되고 위험함. 확장성이 크게 떨어짐.
  
## 3. 현대적인 설계 트렌드 및 최종 결론

과거에는 논리적 명확성, 저장 공간 절약 등의 이유로 식별 관계가 선호되기도 했으나, 소프트웨어의 복잡성이 증가하고 변화의 속도가 빨라진 현대에는 다음과 같은 이유로 **비식별 관계가 사실상의 표준(Best Practice)**으로 자리 잡았음.

- **압도적인 유연성과 민첩성**: 비즈니스 요구사항 변경 시 PK 변경 없이 관계나 규칙을 수정할 수 있음.
- **단순성과 일관성**: 모든 테이블이 비즈니스와 무관한 독립적인 PK(`id`)를 갖는 일관된 구조를 유지하여 이해와 관리가 쉬움.
- **ORM 친화성**: JPA/Hibernate 등 현대적인 개발 프레임워크와 완벽하게 조화를 이룸.
- **비즈니스 로직과의 분리**: 테이블의 '신원(PK)'을 비즈니스 규칙(자연 키)과 분리하여 시스템의 안정성을 높임.

### 데이터베이스 설계의 황금률

1.  **기본 키 (PK)**: 비즈니스와 무관한 **대리 키(Surrogate Key)**를 사용함. (`BIGINT AUTO_INCREMENT`가 일반적)
2.  **관계**: 모든 관계는 **비식별 관계(Non-identifying)**로 설계함.
3.  **비즈니스 규칙**: 데이터 중복 방지 등은 **UNIQUE 제약조건**을 적극 활용하여 보장함.

> **결론**: 변화에 유연하고 오랫동안 사랑받는 안정적인 시스템을 설계하기 위해, **'대리 키-PK, 자연 키-UNIQUE, 관계-비식별'** 원칙을 따르는 것이 최상의 선택임.
