# 4. 개념적 모델링 - 실습 요약

## 1. 실전 요구 사항 분석

-   실제 온라인 쇼핑몰 구축 프로젝트를 기반으로 실습 진행.
-   초기 기획서에는 방대한 기능이 포함되어 있었고, 이를 그대로 구현하면
    일정 내 개발 불가능.
-   훌륭한 개발자는 기술 중심이 아니라 **비즈니스 중심**으로 접근하여
    핵심 기능을 선별해야 함.
-   기획/사업팀과 논의를 통해 1차 출시(MVP)에 필요한 기능만 추려냄.

## 2. MVP 기능 정의

MVP 기능: 
1. 회원 관리
2. 상품 관리
3. 주문
4. 결제
5. 배송

## 3. 핵심 엔티티 도출

-   **회원(Member)**
-   **상품(Product)**
-   **주문(Order)**
-   **결제(Payment)**
-   **배송(Delivery)**

주문과 배송을 분리해 책임을 명확히 하고 관리 단순화.

## 4. 엔티티 속성 정의 및 관계 설정

### 대표 속성

-   회원: 회원id, 로그인id, 비밀번호, 이메일, 주소
-   상품: 상품id, 상품명, 가격, 재고
-   주문: 주문id, 주문 상태, 주문 일시, 배송지 주소
-   결제: 결제id, 결제 방식, 결제 금액, 결제 일시
-   배송: 배송id, 배송 상태, 운송장 번호

### 관계

-   회원 1 : N 주문
-   주문 1 : 1 결제
-   주문 1 : 1 배송
-   주문 M : N 상품

## 5. M:N 관계 해소 --- 주문 항목(order_item)

### M:N 문제점

-   물리적으로 구현 불가능
-   수량, 주문 당시 가격 같은 관계 데이터 저장 불가

### 해결

→ **연관 엔티티 order_item 생성**
- 주문 가격
- 주문 수량

관계 변환: - 주문 1 : N 주문 항목
- 상품 1 : N 주문 항목

## 6. 개념적 모델 ERD

-   핵심 엔티티와 관계를 시각적으로 표현.
-   까마귀발(Crow's Foot) 표기법 사용.
-   개념적 모델에서는 외래 키를 표시하지 않음(기술 종속 배제 목적).

ERD 목적: - 모든 팀이 공통 이해를 가지기 위한 단순화된 지도 역할.

## 7. 용어 사전 작성

### 목적

-   프로젝트 전반에서 **일관된 명칭 사용**
-   엔티티/속성/컬럼명 기준 문서

### 용어 예시

| 명칭       | 영문명      | 설명                         |
|------------|-------------|------------------------------|
| 회원       | member      | 고객 정보                    |
| 상품       | product     | 판매 물건                    |
| 주문       | order       | 주문 정보(테이블명 orders)  |
| 주문 항목  | order_item  | M:N 해소 엔티티              |
| 배송       | delivery    | 배송 처리 정보               |
| 결제       | payment     | 결제 정보                    |


### 속성 용어 예시

-   id: 식별자
-   name: 이름
-   price: 가격
-   quantity: 수량
-   status: 상태
-   address(addr): 주소
-   created_at / updated_at: 생성/수정 시각

### 특징

-   ship_addr, order_price 등 조합 규칙으로 누구나 예측 가능한 이름 생성 가능.
-   실무에서는 Notion/Confluence 등으로 '살아있는 문서'로 관리해야 함.

## 8. 정리

-   실전 모델링은 **복잡한 기능을 단순화하고 핵심부터 구축하는 전략적 과정**.
-   엔티티 도출 → 속성 정의 → 관계 설정 → M:N 해소 → ERD 작성 → 용어
    사전 작성 순서로 진행.
-   용어 사전은 모델링 전체의 기반이 되는 필수 문서.
