# 6. 논리적 모델링2 - 참여도와 일대다 관계 요약

## 1. 관계형 데이터베이스의 관계
- **방향성 없음**: 객체 지향 프로그래밍과 달리, 관계형 데이터베이스의 관계는 방향성이 없음. 외래 키는 두 테이블을 연결할 뿐, `JOIN`을 통해 어느 쪽에서든 자유롭게 데이터를 조회할 수 있음.
- **구현**: 개념적 모델링의 추상적인 관계는 논리적 모델링에서 **외래 키(Foreign Key)**를 통해 구체적으로 구현.

## 2. 관계의 2대 핵심 요소: 카디널리티와 참여도
- **카디널리티(Cardinality)**: 한 테이블의 행이 다른 테이블의 행과 몇 개나 연결될 수 있는지를 나타냄. 
(1:1, 1:N, M:N)
- **참여도(Optionality)**: 관계를 맺는 다른 테이블에 반드시 대응되는 행이 있어야 하는지(필수 참여), 없어도 되는지(선택 참여)를 나타냄.
  - **구현**: 외래 키 컬럼의 `NULL` 허용 여부(`NOT NULL` 또는 `NULL`)로 구현.

## 3. 외래 키(FK) 위치의 중요성: 항상 '다(N)' 쪽에 두어야 함
일대다(1:N) 관계에서 외래 키는 **반드시 '다(N)' 쪽 테이블에 위치해야 함.** 이것은 선택이 아닌, 관계형 데이터베이스의 기본 원칙(정규형)을 지키기 위한 필수 규칙.

- **'일(1)' 쪽에 FK를 두면 안 되는 이유**:
  1.  **제1정규형(1NF) 위반**: 하나의 컬럼에 여러 값을 저장하게 되어 '원자성'을 위배. (예: `member_ids` 컬럼에 '1,2,3'과 같이 저장)
  2.  **데이터 무결성 훼손**: 참조 무결성을 강제할 수 없으며, 데이터 검색 및 수정이 매우 복잡하고 성능이 저하.
  3.  **확장성 부재**: 관계가 추가될 때마다 테이블 구조를 변경해야 하는 끔찍한 설계가 됨.

- **'다(N)' 쪽에 FK를 두는 이유**:
  - 각 행은 단 하나의 값만 가지므로 **원자성**을 준수.
  - 데이터 구조가 안정적이고 **확장성**이 뛰어남.
  - **참조 무결성**을 보장할 수 있음.

## 4. 참여도 구현의 한계와 해결책
- **'다(N)' 쪽의 참여도**: 외래 키에 `NULL` 또는 `NOT NULL` 제약조건을 설정하여 간단하게 제어할 수 있음. (예: 회원은 팀에 소속될 수도, 안 될 수도 있음.)
- **'일(1)' 쪽의 필수 참여**: 데이터베이스 제약조건만으로는 구현이 불가능. (예: '팀은 최소 한 명 이상의 팀원이 있어야 한다'는 규칙)
  - **이유**: '일(1)' 쪽 테이블에는 참조할 외래 키가 없기 때문.
  - **해결책**: **애플리케이션 계층**에서 트랜잭션(Transaction)을 통해 비즈니스 로직으로 구현. (예: 팀 생성과 팀원 추가를 하나의 트랜잭션으로 묶음)

## 5. 조인(JOIN)과 데이터 뻥튀기
- **다대일(N:1) 조인**: '다(N)' 쪽(예: `member`)을 기준으로 '일(1)' 쪽(예: `team`)을 조인하면, 기준 테이블의 행 수가 유지되며 데이터 뻥튀기가 발생하지 않음.
- **일대다(1:N) 조인**: '일(1)' 쪽을 기준으로 '다(N)' 쪽을 조인하면, 기준 테이블의 행이 'N' 쪽 데이터만큼 복제되어 결과 행의 수가 늘어남. 이를 **데이터 뻥튀기**라고 함.
  - 이 현상은 오류가 아니며, '특정 팀에 속한 모든 팀원'을 조회하는 등 자연스러운 기능 구현에 사용.
  - `GROUP BY`나 집계 함수(`COUNT`, `SUM` 등) 사용 시 이 현상을 인지하지 못하면 잘못된 결과가 나올 수 있으므로 반드시 이해해야 함.
